Решение описано после задания.

ЗАДАНИЕ:
Любые входящие или исходящие звонки абонентов нашего оператора фиксируются в СDR файле, который собирается на коммутаторе. Данные поступают в виде записей типа:

тип вызова (01 - исходящие, 02 - входящие);

номер обслуживаемого абонента;

номер абонента, с которым осуществлялась связь;

дата и время начала звонка (ISO 8601);

дата и время окончания звонка (ISO 8601);

разделитель данных – запятая;

разделитель записей – перенос строки;

данные обязательно формируются в хронологическом порядке;

в рамках задания CDR может быть обычным txt/csv;

Каждые 10 записей составляют CDR, который отправляется на тарификацию в сервис BRT.

При этом, если звонок начинается до полуночи, а заканчивается после, коммутатор генерирует по такому звонку 2 записи в CDR.

Вот пример фрагмента CDR:

02,79876543221, 79123456789, 2025-02-10T14:56:12, 2025-02-10T14:58:20

01,79996667755, 79876543221, 2025-02-10T10:12:25, 2025-02-10T10:12:57

Задача 1:

Напишите сервис, эмулирующий работу коммутатора, т.е. генерирующий записи действий абонента и собирающий из них CDR файлы.

Условия:

1. Установленный список абонентов (не менее 10) хранится в локальной БД (h2); Данные о звонках помещаются в соседнюю таблицу этой БД.

2. CDR собирается из записей, которые могут генерироваться параллельно; (НЕ РЕАЛИЗОВАНО ПОКА)

3. На один месяц может приходится случайное количество CDR файлов. Тарифицируемый период в рамках задания - 1 год;

4. Данные в CDR идут не по порядку, т.е. записи по одному абоненту могут быть в разных частях файла;

5. Хронология звонков при этом должна обязательно соблюдаться;

6. Количество и длительность звонков определяется случайным образом;

7. CDR, по мере генерации, асинхронно отправляются в сервис BRT через брокер сообщений.
                                                                   
РЕШЕНИЕ: 
Микросервис cdr представляет собой эмуляцию работы реального коммутатора, его задачи:
1. Сгенерировать 10 пользователей и сохранить в ин-мемори БД H2
2. Сгенерировать n кол-во CDR записей и сохранить в ин-мемори БД H2
3. Каждые 10 сгенерированных записей отправилять в брокер сообщений для обработки brt сервисом

Сообщения посылаются в формате Json

Генерация данных происходит в момент обновления спринг контекста - когда он собран. 

Генераторы данных расположены в методах com.mobile.network.report.service.impl.CustomerServiceImpl#generateCustomers 
и для CDR com.mobile.network.report.service.impl.CDRRecordGeneratorServiceImpl#generateCDRRecords

Настройка RabbitMQ exchange, queue, binding и routing key автоматически происходит при старте приложения благодаря конфигурации в классе RabbitMQConfiguration, 
что позволяет использовать RabbitTemplate для отправки без доп настроек, уже полностью сконфигурированным.

CDR записи генерируются по переданному году, алгоритм генерации:
1. Получаем все номера пользователей из базы
2. Рандомизируется кол-во звонков в год от 100 до 599 totalCalls
3. Вычисляется кол-во секунд в году totalSecondsInYear = endOfYear - startOfYear
4. Вычисляется средний интервал между звонками averageIntervalSeconds = totalSecondsInYear / totalCalls
5. В цикле начиная с начала года:
6. Проверяется список для последующей отправки в брокер, если ровно 10 записей в нем, отправляем их в брокер, список очищаем (ВРЕМЕННОЕ РЕШЕНИЕ)
7. Вычисляется интервал, к среднему добавляется случайное отклонение
8. Проверяется что время не вышло за границы года
9. Генерируется одиночная запись CDRRecordDto
10. Получаем два случайных номера, если она совпадают, присваиваем второму новый номер пока они не будут разными
11. Рандомизируем CallType 01 или 02
12. Рандомизируем длительность разговора от 10 до 600 секунд
13. Длительность звонка вычисляется как сумма начала звонка и длительности разговора
14. Собранный объект добавляется в список для последующего сохранения
15. Собранный объект добавляется в список для последующей отправки в брокер
16. После цикла проверка есть ли в списоке для последующей отправки в брокер еще записи, если есть - отправка в брокер (на случай генерации не кратного 10-ти кол-ва записей)

В качестве базы используется H2, работа с ней происходит посредством Spring JPA

Из сторонних библиотек были использованы:

Mapstruct для уменьшения шаблонного кода генерации мапперов дто -> ентити

Lombok для уменьшения бойлерплейт кода
